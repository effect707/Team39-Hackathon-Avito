# Распределение задач команды «Авито Честная очередь»

**Состав:** 3 backend-разработчика, 1 frontend-разработчик

**Срок:** 7 календарных дней

**Источник требований:** `docs/spec.md`
**Инженерные правила:** `AGENTS.md`

## 1. Общий принцип работы

Каждый участник владеет своим модулем, его тестами и документацией. Владение не означает, что только этот человек может изменять файлы модуля, но существенные изменения должны проходить его review.

Команда делает один модульный Go-монолит, а не четыре независимых сервиса. PostgreSQL является источником истины, а GORM — основным ORM и способом реализации repositories. Для явных конкурентно-критичных запросов разрешён параметризованный raw SQL. Очередь, резерв и checkout должны работать корректно при двух экземплярах API, поэтому память процесса и `sync.Mutex` не используются как бизнес-гарантия.

## 2. Краткая карта ответственности

| Участник | Главная зона | Результат к концу недели |
|---|---|---|
| Backend 1 | Platform, DevOps, SSE и интеграция | Весь проект собирается, работает на сервере, доставляет realtime-обновления и проверяется нагрузочным сценарием |
| Backend 2 | FIFO Queue Engine | Пользователь идемпотентно получает строгое место, видит позицию и не может обойти более ранних участников |
| Backend 3 | Inventory, Grant, Worker и Checkout | Товар безопасно резервируется, право истекает и передаётся следующему, checkout нельзя обойти |
| Frontend | Полный пользовательский путь | Все состояния очереди доступны через понятный адаптивный интерфейс |

## 3. Backend 1 — Platform, DevOps, realtime и интеграция

Эту роль берёт участник, который хочет заниматься DevOps и дополнительной backend-разработкой.

### Зона владения

- `backend/cmd/api`;
- `backend/internal/platform`;
- `backend/internal/events`;
- общая HTTP-инфраструктура;
- `deploy/nginx`;
- `tools/loadgen`;
- `Dockerfile`, `docker-compose.yml`, `Makefile`;
- CI, observability и публичный Ubuntu-деплой.

### Backend-задачи

1. Создать каркас Go-приложения:
   - загрузка и валидация конфигурации;
   - подключение к PostgreSQL через GORM и `gorm.io/driver/postgres`;
   - настройка underlying `database/sql` connection pool;
   - graceful shutdown;
   - общий router;
   - dependency wiring модулей.
2. Реализовать общие HTTP-компоненты:
   - `request_id`;
   - structured logging;
   - recovery middleware;
   - CORS при необходимости;
   - единый JSON-формат ошибок;
   - demo-auth через `X-Demo-User-ID`.
3. Реализовать endpoints:
   - `GET /api/v1/health`;
   - `GET /api/v1/ready`.
4. Реализовать realtime:
   - PostgreSQL `LISTEN/NOTIFY`;
   - выделенное закреплённое соединение для `LISTEN`, отдельное от обычных GORM repository-запросов;
   - транзакционный `NOTIFY` через GORM `tx.Exec`;
   - менеджер локальных SSE-подключений;
   - `GET /api/v1/products/{product_id}/queue/events`;
   - heartbeat и корректное закрытие соединения;
   - reconnect-сценарий совместно с frontend.
5. Связать HTTP handlers Backend 2 и Backend 3 с общим приложением.
6. Реализовать минимальные метрики:
   - число активных SSE-подключений;
   - длительность join/promotion;
   - число выданных и просроченных прав;
   - checkout rejections по причинам.
7. Создать load generator для сценария 100 пользователей и 5 единиц.

### DevOps-задачи

1. Подготовить Dockerfile для frontend, API и worker.
2. Подготовить Docker Compose с сервисами:
   - `frontend`;
   - `nginx`;
   - `api-1`;
   - `api-2`;
   - `worker`;
   - `postgres`;
   - `migrate`.
3. Настроить Nginx:
   - раздача frontend;
   - балансировка между `api-1` и `api-2`;
   - проксирование REST;
   - отключение buffering для SSE;
   - увеличенный timeout для SSE.
4. Создать `.env.example`, healthchecks и PostgreSQL volume.
5. Настроить CI:
   - backend format/lint/test;
   - frontend lint/test/build;
   - проверка production-сборки.
6. Развернуть приложение на Ubuntu-сервере.
7. Настроить публичный адрес, TLS и простой способ посмотреть логи.
8. Подготовить резервный demo-сценарий на случай сбоя публичного сервера.

### Критерии приёмки роли

- `docker compose up --build` запускает проект без ручной настройки;
- Nginx распределяет запросы между двумя API-репликами;
- SSE работает через Nginx и восстанавливается после reconnect;
- отключение одной API-реплики не теряет место пользователя;
- loadgen подтверждает результат `5 GRANTED + 95 WAITING`;
- публичная ссылка открывается на чистом устройстве;
- `make verify` запускает все основные проверки.

## 4. Backend 2 — FIFO Queue Engine

### Зона владения

- `backend/internal/queue`;
- таблица `queue_entries`;
- поле `products.next_ticket`;
- queue-часть OpenAPI;
- unit и PostgreSQL integration tests очереди.

### Задачи

1. Совместно с командой зафиксировать состояния и разрешённые переходы заявки.
2. Подготовить queue-часть миграции:
   - `queue_entries`;
   - уникальность `(product_id, ticket_no)`;
   - частичная уникальность активной заявки `(product_id, user_id)`;
   - необходимые индексы позиции и promotion.
3. Реализовать GORM repository для заявок; блокировки выполнять через `clause.Locking` или параметризованный raw SQL, когда он делает семантику PostgreSQL понятнее.
4. Реализовать атомарное назначение `ticket_no` под блокировкой товара.
5. Реализовать идемпотентный join:
   - повторный запрос возвращает существующую активную заявку;
   - повторный вход после терминального неуспеха получает новый номер в хвосте;
   - `SOLD_OUT` не создаёт новую активную заявку.
6. Реализовать расчёт текущей позиции по меньшим активным `ticket_no`.
7. Реализовать получение состояния пользователя после reload.
8. Реализовать выход пользователя:
   - `WAITING` → `CANCELLED`;
   - передача отказа от `GRANTED` в общий allocation-сервис Backend 3.
9. Реализовать закрытие очереди при полной продаже товара.
10. Подготовить handlers и контракты:
   - `POST /api/v1/products/{product_id}/queue/join`;
   - `GET /api/v1/products/{product_id}/queue/me`;
   - `DELETE /api/v1/products/{product_id}/queue/me`.
11. Отправлять доменное событие после изменения заявки, чтобы Backend 1 доставил SSE-уведомление.

### Обязательные тесты

- повторный join создаёт одну активную заявку;
- конкурентные join получают уникальные монотонные `ticket_no`;
- позиция соответствует числу меньших активных номеров;
- cancelled/terminal заявки не учитываются в позиции;
- новая заявка не обходит существующего `WAITING`, даже если появилась свободная единица;
- пользователь после повторного входа попадает в хвост;
- перезапуск API не меняет порядок;
- 100 пользователей при 5 единицах дают ожидаемое распределение совместно с Backend 3.

### Критерии приёмки роли

- FIFO определяется только серверным `ticket_no`;
- у пользователя не возникает двух активных заявок на товар;
- endpoints соответствуют OpenAPI;
- очередь корректна при конкурентных запросах через две API-реплики;
- интеграционные тесты работают против настоящего PostgreSQL.

## 5. Backend 3 — Inventory, Purchase Grant, Worker и Checkout

### Зона владения

- `backend/internal/allocation`;
- `backend/internal/checkout`;
- `backend/cmd/worker`;
- таблицы `inventory_units`, `purchase_grants`, `checkout_attempts`;
- grant/checkout-часть OpenAPI;
- конкурентные тесты резерва и checkout.

### Задачи

1. Подготовить миграции и ограничения:
   - состояния товарных единиц;
   - состояния прав;
   - одна активная grant-запись на товарную единицу;
   - `expires_at`, `consumed_at`;
   - уникальный `idempotency_key` mock payment callback.
2. Реализовать GORM repositories для units, grants и checkout attempts; не использовать `Save` для переходов состояний, проверять `RowsAffected` после условных updates.
3. Реализовать единый allocation/promotion-сервис, который вызывается из:
   - join;
   - expiry;
   - добровольного отказа;
   - payment failure/timeout.
4. Allocation должен:
   - блокировать данные в согласованном порядке;
   - выбирать свободные товарные единицы;
   - выбирать `WAITING` по минимальному `ticket_no`;
   - создавать персональное право с TTL;
   - не выдавать одну единицу дважды.
5. Реализовать worker:
   - поиск просроченных прав;
   - `FOR UPDATE SKIP LOCKED`;
   - перевод права в `EXPIRED`;
   - освобождение единицы;
   - продвижение следующего пользователя.
6. Реализовать checkout guard:
   - проверка владельца;
   - проверка товара;
   - проверка статуса;
   - проверка TTL по времени PostgreSQL;
   - защита от повторного использования;
   - атомарный переход в `CHECKOUT_PENDING`.
7. Реализовать mock payment:
   - `success` → `PURCHASED` и `SOLD`;
   - `failure/timeout` → освобождение единицы и promotion;
   - повторный callback не меняет итог.
8. Подготовить endpoints:
   - `POST /api/v1/grants/{grant_id}/checkout`;
   - `POST /api/v1/demo/grants/{grant_id}/payment-result`.
9. Публиковать доменные события для SSE после commit.

### Обязательные тесты

- у одной единицы не бывает двух активных прав;
- истечение прав участников 1–5 продвигает номера 6, 7 и далее;
- два worker не обрабатывают одно право дважды;
- checkout без права отклоняется;
- чужое право отклоняется;
- право на другой товар отклоняется;
- просроченное и использованное право отклоняются;
- одновременные expiry и checkout дают ровно один результат;
- повторный payment callback идемпотентен;
- failure/timeout освобождает ровно одну единицу и продвигает одного следующего участника.

### Критерии приёмки роли

- резерв временный, персональный и одноразовый;
- oversell невозможен на уровне транзакций и ограничений БД;
- новый grant всегда получает минимальный активный `WAITING.ticket_no`;
- worker безопасно запускается в нескольких экземплярах;
- checkout нельзя обойти прямым запросом.

## 6. Frontend-разработчик — полный пользовательский путь

### Зона владения

- каталог и карточка товара;
- demo-user switcher;
- экраны очереди, права, checkout и результатов;
- REST/SSE-клиент;
- frontend tests, ESLint, Prettier и production build.

### Задачи

1. Поднять React 18+ приложение на TypeScript и Vite.
2. Подключить TanStack Query, UI-kit, ESLint и Prettier.
3. Создать API types в соответствии с `docs/openapi.yaml`.
4. Реализовать demo-user switcher, который устанавливает `X-Demo-User-ID`.
5. Реализовать карточку товара:
   - название, изображение, цена;
   - предварительное состояние;
   - кнопка «Купить»;
   - переход к альтернативам при `SOLD_OUT`.
6. Реализовать состояния:
   - `JOINING`;
   - `WAITING` с позицией;
   - `GRANTED` с таймером;
   - `CHECKOUT_PENDING`;
   - `PURCHASED`;
   - `EXPIRED`;
   - `PAYMENT_FAILED`;
   - `SOLD_OUT`;
   - `CANCELLED`;
   - восстановимую сетевую ошибку.
7. Реализовать SSE:
   - подключение после получения заявки;
   - refetch REST-состояния после события;
   - reconnect;
   - восстановление состояния после reload.
8. Реализовать таймер по серверному `expires_at`. Истечение таймера на клиенте не должно самостоятельно менять бизнес-статус.
9. Реализовать mock checkout с результатами success/failure/timeout.
10. Реализовать до пяти альтернативных объявлений.
11. Сделать интерфейс адаптивным от 360 px и доступным с клавиатуры.

### Обязательные тесты

- корректное отображение каждого состояния;
- повторный клик по join не создаёт визуальные дубли;
- SSE-событие вызывает refetch;
- reconnect и reload восстанавливают статус;
- таймер использует `expires_at`;
- кнопка checkout доступна только при `GRANTED`;
- error screen сообщает, что место сохранено;
- sold-out и неуспешная покупка показывают альтернативы.

### Критерии приёмки роли

- через UI можно пройти все основные и исключительные сценарии;
- пользователь всегда понимает текущий статус и следующий шаг;
- frontend не вычисляет самостоятельно право, остаток или истинное место;
- production build, lint и tests проходят в CI;
- интерфейс работает на мобильной и desktop-ширине.

## 7. Общие задачи всей команды

### День 1

Все четыре участника совместно фиксируют до начала параллельной разработки:

- state machine;
- схему БД v1;
- OpenAPI v1;
- формат ошибок;
- порядок блокировок;
- TTL и demo-настройки;
- основной demo-сценарий.

После фиксации изменения общей схемы или контракта обсуждаются со всеми затронутыми участниками.

### Ежедневно

- короткая синхронизация утром: результат дня, зависимость, блокер;
- интеграция в общую ветку минимум один раз в день;
- review критического кода вторым backend-разработчиком;
- обновление OpenAPI и документации одновременно с изменением поведения;
- проверка публичного стенда начиная со второго дня.

### Общая ответственность

- `README.md` и описание архитектуры;
- прозрачный раздел об использовании ИИ;
- seed-данные;
- репетиция демонстрации;
- отсутствие секретов в репозитории;
- исправление блокирующих дефектов независимо от формального владельца.

## 8. Зависимости между участниками

| Поставщик | Что передаёт | Потребитель | Срок |
|---|---|---|---|
| Вся команда | State machine, схема и OpenAPI v1 | Все | Конец дня 1 |
| Backend 1 | Каркас, DB pool, middleware и error format | Backend 2 и 3 | День 1–2 |
| Backend 2 | Join/status contracts и queue events | Backend 1 и Frontend | День 2–3 |
| Backend 3 | Allocation/grant/checkout contracts | Backend 2, Backend 1 и Frontend | День 2–3 |
| Backend 1 | SSE endpoint и тестовый стенд | Frontend | День 3–4 |
| Frontend | Проверенный пользовательский путь | Вся команда | День 4–6 |
| Backend 1 | Loadgen и публичный стенд | Backend 2 и 3 | День 4–5 |

Если зависимость задерживается, поставщик сначала отдаёт рабочий контракт и stub, чтобы другой участник не останавливался.

## 9. Распределение code review

- Backend 1 проверяет конфигурацию, HTTP, observability и deploy-изменения.
- Backend 2 проверяет FIFO, порядок `ticket_no` и queue state transitions.
- Backend 3 проверяет транзакции allocation, TTL и checkout guard.
- Frontend проверяет пользовательские тексты, состояния и соответствие API.
- Критические SQL-транзакции должны получить review минимум от двух backend-разработчиков.

Автор не принимает собственный критический модуль без второго review.

## 10. План по дням

| День | Цель команды |
|---|---|
| 1 | Контракты зафиксированы, каркас и Compose запускаются |
| 2 | Работают базовые join, grant и UI на согласованных контрактах |
| 3 | Работают status, leave, promotion, worker и восстановление состояния |
| 4 | Работают SSE, checkout guard, mock payment и все терминальные экраны |
| 5 | Проходят конкурентные тесты, две API-реплики и сценарий 100/5 |
| 6 | Готов публичный release candidate, документация и E2E |
| 7 | Заморозка функций, исправление дефектов и две репетиции демо |

После середины шестого дня команда не добавляет новые возможности. Приоритет получают корректность FIFO, защита checkout, воспроизводимость запуска и понятная демонстрация.

## 11. Когда работа участника считается завершённой

Участник закончил свою часть, если:

- выполнены его критерии приёмки;
- сохранены бизнес-инварианты из `docs/spec.md`;
- проходят релевантные unit и integration tests;
- обновлены OpenAPI, конфигурация и README;
- код прошёл review владельцев затронутых модулей;
- результат доступен в общей сборке, а не только в локальной ветке;
- участник может за две минуты показать свой сценарий на публичном стенде.
