# AGENTS.md

## 1. Назначение

Этот репозиторий содержит хакатонный MVP «Авито Честная очередь»: строгую FIFO-очередь перед checkout для дефицитных товаров, временное персональное право на покупку и автоматическую передачу освободившейся товарной единицы следующему пользователю.

Инструкции обязательны для людей и AI-агентов, которые изменяют код, тесты, инфраструктуру или документацию. Они действуют для всего репозитория. Если в подкаталоге появится более конкретный `AGENTS.md`, он может уточнять, но не отменять бизнес-инварианты этого документа.

## 2. Источники истины и приоритеты

1. `docs/spec.md` — продуктовые требования, сценарии, состояния и Definition of Done.
2. `docs/openapi.yaml` — публичный HTTP-контракт.
3. Миграции PostgreSQL — фактическая схема данных.
4. Тесты — проверяемые примеры поведения, но они не могут молча менять требования спецификации.

При противоречии остановись, явно опиши расхождение и сначала согласуй изменение спецификации или контракта. Не придумывай новое продуктовое поведение по аналогии с маркетплейсами.

Приоритет работы:

1. сохранение бизнес-инвариантов и защита checkout;
2. завершённый сквозной пользовательский путь;
3. тестируемость и восстановление после сбоев;
4. понятный интерфейс и демонстрация;
5. оптимизации и дополнительные функции.

## 3. Обязательный стек и ограничения кейса

### Frontend

- React 18+;
- TypeScript;
- Vite;
- TanStack Query для серверного состояния;
- выбранный UI-kit, предпочтительно Material UI;
- ESLint и Prettier.

### Backend и данные

- Go;
- PostgreSQL как единственный источник истины;
- GORM (`gorm.io/gorm`) как основной ORM;
- PostgreSQL dialect `gorm.io/driver/postgres`, использующий `pgx` под `database/sql`;
- параметризованный raw SQL там, где он лучше выражает конкурентно-критичную семантику PostgreSQL;
- REST/JSON и SSE;
- миграции в `backend/migrations`;
- `gofmt`, `go vet`, `golangci-lint`, `go test` и `go test -race` для критических пакетов;
- `.golangci.yaml` строго в корне репозитория.

### Запуск и поставка

- один репозиторий для frontend и backend;
- backend-only Docker Compose с двумя напрямую опубликованными API-репликами;
- независимые build и deploy frontend под ответственностью frontend-разработчика;
- отдельный Go worker для TTL;
- README, `.env.example`, OpenAPI и воспроизводимый seed;
- публичный Ubuntu-деплой.

Не добавляй Redis, Kafka, Kubernetes, отдельные микросервисы, реальную авторизацию, реальную оплату или AI-интеграцию без явно согласованного изменения scope. В MVP не должно быть случайного розыгрыша: порядок только строгий FIFO.

## 5. Неприкосновенные бизнес-инварианты

Любое изменение обязано сохранять все условия:

1. Число зарезервированных и проданных единиц не превышает исходный остаток.
2. У одной товарной единицы не более одного активного права.
3. У пользователя не более одной нетерминальной заявки на один товар.
4. `(product_id, ticket_no)` уникальна.
5. Следующее право получает активная заявка `WAITING` с минимальным `ticket_no`.
6. Новая заявка не получает свободную единицу в обход более ранней `WAITING`-заявки.
7. Право действует только для указанных `user_id`, `product_id` и `inventory_unit_id`.
8. Право временное, непередаваемое и одноразовое.
9. Checkout без подходящего активного права всегда отклоняется.
10. Терминальная заявка не возвращается в активное состояние; повторный вход создаёт новый номер в хвосте очереди.
11. Одновременные expiry и checkout дают ровно один итог.
12. HTTP retry и повторный payment callback не дублируют эффект.
13. Перезапуск API или worker не меняет порядок очереди и не теряет состояние.

Нельзя использовать `sync.Mutex` или память процесса как гарантию этих условий. Mutex допустим только для локальной технической структуры, которая не определяет товарный остаток, очередь, право или checkout.

## 6. Транзакции и конкурентность

- Все решения о порядке, остатке, TTL и праве принимает backend по данным PostgreSQL.
- Обычные repository-запросы реализуй через GORM. Не обходи GORM без причины, но используй параметризованный raw SQL, когда `clause.Locking` или query builder делают критичную семантику блокировки менее очевидной.
- Бизнес-транзакцию открывай через `db.WithContext(ctx).Transaction(...)` и передавай полученный `tx` во все repository-операции этой транзакции. Не смешивай внутри неё `tx` и корневой `db`.
- Для операции, изменяющей состояние товара, сначала блокируй строку `products` через `SELECT ... FOR UPDATE`.
- В GORM выражай блокировки через `clause.Locking{Strength: "UPDATE"}` и при необходимости `Options: "SKIP LOCKED"`; проверяй сгенерированное поведение интеграционным тестом.
- Назначай и увеличивай `products.next_ticket` в одной транзакции.
- После `products` блокируй связанные записи всегда в одном порядке, чтобы снижать риск deadlock.
- Выбор следующего участника выполняй по минимальному `ticket_no`, а не по `created_at`.
- Join, expiry, отказ и payment failure должны использовать один общий allocation/promotion-сервис. Не делай отдельный «быстрый» grant в join, который может обойти старую `WAITING`-заявку.
- Worker может распределять независимые задания через `FOR UPDATE SKIP LOCKED`.
- Сравнивай TTL с временем PostgreSQL. Клиентские часы не авторитетны.
- Изменение состояния и `NOTIFY` создавай в одной транзакции. PostgreSQL доставит уведомление после commit.
- Вызывай `NOTIFY` через транзакционный GORM `tx.Exec`. Для `LISTEN` events-модуль должен владеть выделенным закреплённым соединением; не выполняй session-level подписку через произвольное соединение общего пула.
- Не держи транзакцию открытой во время HTTP-вызова, SSE-отправки или имитации оплаты.
- Добавляй уникальные/частичные индексы и `CHECK` constraints там, где инвариант можно закрепить в БД.
- Не используй `Save` для state transitions: его upsert-поведение может создать запись, когда условный update не нашёл строку. Используй явные `Where(...).Updates(...)` и проверяй `RowsAffected`.
- При обновлении zero-value полей используй `map` или явный `Select`, поскольку struct updates GORM по умолчанию пропускают zero values.
- Не прячь state machine, allocation или promotion в GORM hooks.
- Обрабатывай ожидаемые conflicts идемпотентно; не маскируй их слепыми бесконечными retry.

Если предлагается более быстрый алгоритм, сначала докажи интеграционным тестом, что он сохраняет FIFO и отсутствие oversell при двух API-репликах и двух worker.

## 7. State machine

Пользовательские состояния: `JOINING`, `WAITING`, `GRANTED`, `CHECKOUT_PENDING`, `PURCHASED`, `EXPIRED`, `PAYMENT_FAILED`, `SOLD_OUT`, `CANCELLED`, `ERROR`.

Разрешённые переходы фиксируй централизованно и покрывай unit-тестами. Не присваивай статусы произвольно из handlers или repositories.

Ключевые переходы:

- join → `GRANTED`, если есть свободная единица;
- join → `WAITING`, если непроданные единицы временно заняты;
- join → `SOLD_OUT`, если все единицы проданы или товар снят;
- `WAITING` → `GRANTED` только через FIFO promotion;
- `GRANTED` → `CHECKOUT_PENDING` только после checkout guard;
- `GRANTED` → `EXPIRED` или `CANCELLED` с освобождением единицы;
- `CHECKOUT_PENDING` → `PURCHASED` при mock success;
- `CHECKOUT_PENDING` → `PAYMENT_FAILED` при failure/timeout с освобождением единицы;
- `WAITING` → `SOLD_OUT`, когда больше не осталось непроданных единиц.

Каждое пользовательское состояние должно иметь русскоязычное сообщение и явный следующий шаг.

## 8. Checkout guard

Endpoint checkout обязан внутри одной атомарной операции проверить:

- demo-идентичность пользователя из доверенного middleware;
- существование права;
- совпадение пользователя и товара;
- допустимый статус права;
- `expires_at > now()` по времени БД;
- отсутствие предыдущего использования.

После успешной проверки право атомарно становится `CHECKOUT_PENDING`. Никогда не доверяй `user_id`, `product_id`, статусу или времени из тела запроса. Не раскрывай чужое право различающимися подробными ошибками.

Mock payment callback должен иметь `idempotency_key`. `success` продаёт ровно одну единицу; `failure` и `timeout` освобождают её и запускают тот же общий promotion-сервис.

## 9. REST, SSE и ошибки

- Изменение `docs/openapi.yaml` и реализация endpoint должны попадать в одну задачу/PR.
- Не меняй публичные поля или коды ошибок молча.
- Используй стабильный envelope ошибки с `code`, `message`, `request_id`.
- `X-Demo-User-ID` извлекается middleware; бизнес endpoints не принимают `user_id` в JSON.
- Demo-only endpoints защищаются конфигурацией и выключаются вне demo-режима.
- SSE сообщает только о возможном изменении. После события frontend перечитывает REST-состояние.
- Потеря SSE, reconnect или несколько одинаковых событий не должны влиять на очередь.
- Go API отдаёт SSE напрямую; любой добавленный frontend-командой промежуточный слой не должен буферизовать поток.

## 10. Миграции и данные

- Миграции применяются последовательно и хранятся в репозитории.
- Версионируемые SQL-миграции являются единственным источником схемы. Не запускай GORM `AutoMigrate` в API, worker, Compose entrypoint или production/development startup.
- Не редактируй уже применённую общую миграцию; добавь новую.
- Каждая миграция должна иметь безопасный порядок создания/удаления зависимостей.
- Seed идемпотентен и создаёт минимум товар с одной единицей, товар с несколькими единицами, альтернативные объявления и demo-пользователей.
- Тесты не зависят от порядка UUID или неявного физического порядка строк.
- Не очищай пользовательскую или общую БД разрушительными командами ради локального теста.

## 11. Frontend-правила

- TanStack Query хранит серверное состояние; локальный React state — только UI-состояние.
- После reload состояние восстанавливается через `GET .../queue/me`, а не через локальную копию позиции.
- Таймер строится от серверного `expires_at`, но backend повторно проверяет TTL при действии.
- Кнопки защищают от случайного двойного клика, но backend всё равно обязан быть идемпотентным.
- Обработай loading, reconnect, error и все терминальные состояния.
- Интерфейс адаптивен от 360 px и доступен с клавиатуры; у основных действий есть понятные labels/focus states.
- Пользовательские тексты — на русском. Имена типов, функций и API-полей — на английском.
- Не вычисляй на клиенте «настоящее» место в очереди, остаток или право на checkout.

В первый день команда совместно фиксирует state machine, миграции v1 и OpenAPI до параллельной реализации.

## 13. Рабочий процесс

Перед изменением:

1. Найди соответствующее требование и acceptance criteria в `docs/spec.md`.
2. Определи затронутые состояния, инварианты, контракт и владельцев.
3. Для бизнес-логики сначала добавь или уточни тест, воспроизводящий требуемое поведение.
4. Делай минимальное сквозное изменение без несогласованного расширения scope.

Во время изменения:

- не переформатируй и не переписывай несвязанные файлы;
- не коммить секреты, реальные токены, `.env` и production-данные;
- используй небольшие функции и осмысленные имена;
- размещай интерфейс со стороны потребителя, если он действительно нужен;
- оборачивай ошибки с контекстом, сохраняя возможность `errors.Is/As`;
- пиши структурированные логи без секретов и персональных данных;
- не оставляй `TODO` в критическом пути без issue и владельца.

После изменения:

1. Запусти форматирование и проверки затронутого модуля.
2. Запусти интеграционные тесты при изменении SQL, транзакций, очереди, grant или checkout.
3. Обнови OpenAPI, README и `.env.example`, если изменился контракт или запуск.
4. Кратко опиши риск, тесты и ручной demo-path в PR/передаче задачи.

## 15. Обязательные тесты

Изменение критического пути не считается готовым без соответствующих проверок. Финальный набор обязан включать:

1. 100 конкурентных join при 5 единицах → ровно 5 `GRANTED`, 95 `WAITING`.
2. Истечение двух прав → grant получают `ticket_no` 6 и 7.
3. Два worker не выдают право одному entry дважды.
4. Повторный join создаёт не более одной активной заявки.
5. Checkout без права отклоняется.
6. Чужое, просроченное и использованное право отклоняется.
7. Одновременные checkout и expiry дают один итог.
8. Повторный payment callback идемпотентен.
9. Перезапуск API/worker не меняет FIFO.
10. Потеря SSE не меняет состояние, а reconnect восстанавливает UI через REST.

Тесты конкурентности запускаются против настоящего PostgreSQL, а не только против mock repository.

## 16. Документация и прозрачность ИИ

README должен объяснять бизнес-задачу, архитектуру, FIFO-гарантии, запуск, seed, demo-сценарий, тесты, публичную ссылку, ограничения MVP и выбор PostgreSQL.

В разделе «Использование ИИ» перечисли, где команда использовала AI, какие решения проверила вручную и что пользовательские данные не отправляются во внешние AI-сервисы. Не утверждай, что в продукт встроен AI, если интеграции нет.

### Комментарии в коде

- По умолчанию не добавляй комментарии в код.
- Делай код понятным через точные имена, небольшие функции, явные типы и простую структуру.
- Не комментируй очевидные действия, не пересказывай синтаксис и не добавляй декоративные заголовки над блоками кода.
- Комментарий допустим только когда без него нельзя понять неочевидную причину решения, бизнес-инвариант, ограничение конкурентности, внешний workaround или требование инструмента.
- Обязательная документация экспортируемого API добавляется только там, где её требует выбранный линтер или публичный контракт.
- Перед добавлением комментария сначала попробуй упростить код или улучшить название. Если комментарий всё же нужен, объясняй «почему», а не «что делает код».

## 17. Definition of Done для любой задачи

Задача готова только если:

- выполнены acceptance criteria из `docs/spec.md`;
- сохранены все бизнес-инварианты;
- добавлены и проходят релевантные тесты;
- форматирование и линтеры проходят;
